## 0. Korrektur zum ersten Durchgang

**Du hattest recht — die RLS-Sache war schon erledigt.** Mein erster „kritischer" Befund war ein
Testfehler auf meiner Seite, nicht ein Befund.

Ich hatte mit einem leeren Body getestet:

```
PATCH /rest/v1/etappen?id=eq.0000…0000   -d '{}'   → HTTP 200
```

Ohne Spalte im Body prüft Postgres gar keinen Spalten-Grant, und RLS filtert nur Zeilen — ein
UPDATE über 0 Zeilen ist kein Fehler. Das 200 bedeutete also **nichts**. Mit echtem Body:

| Request | Antwort |
|---|---|
| `{"veto":true}` | `204` — erlaubt (vom Dashboard gebraucht) |
| `{"monolog_final":"x"}` | **`401 permission denied`** |
| `{"pipeline_status":"x"}` | **`401 permission denied`** |
| `{"stil_bewertung":2}` | **`401 permission denied`** |

Die Migration `20260723150000_anon_grants_verschaerfen.sql` (Commit `01a387a`) ist gelaufen und
wirkt. `anon` darf per UPDATE nur noch:

- **`etappen`** → `veto`, `freigabe`, `hitl1_entschieden_um`, `hitl_prio_stil`, `reel_varianten`,
  `startort`, `zielort`
- **`stile`** → `aktiv`, `bewertung`

RLS ist auf allen Tabellen aktiv. `INSERT`/`DELETE` haben für `anon` keine Policy und sind damit
blockiert (das kann ich nicht zerstörungsfrei beweisen, aber es folgt zwingend aus den Policies:
RLS an + keine passende Policy = deny).

**Was ich streiche:** „monolog_final überschreiben", „hitl1_entschieden_um fälschen", „alle
Stil-Bewertungen umschreiben". Falsch. Das Restrisiko ist deutlich kleiner — siehe S-1.

**Und der eigentliche Fund:** Dieselbe Migration hat zwei Dashboard-Funktionen kaputtgemacht.
Siehe B-1 und B-2 — das sind die wichtigsten Punkte in diesem Dokument.

## 5. 🟡 Sicherheit — was noch offen ist

### S-1 — Restrisiko der erlaubten Spalten

Ohne Auth kann jeder, der den Quelltext liest:

- `veto` / `freigabe` auf jeder Etappe setzen → ein Reel stoppen oder sofort rausschicken
- **`reel_varianten` überschreiben** → das sind die Narrator-Texte, die publiziert werden
- `startort`/`zielort`/`hitl_prio_stil` ändern
- alle Stil-Bewertungen umschreiben (`aktiv`, `bewertung`)

`reel_varianten` ist der unangenehmste davon. Die Policies sind zudem `USING(true)` /
`WITH CHECK(true)` (Advisor: 2× `rls_policy_always_true`) — die Spalten-Grants sind also die
**einzige** Schutzschicht. Wer versehentlich einen Grant weitet, macht die Spalte sofort
weltschreibbar.

Ob dir das reicht, ist eine Risikoentscheidung: die URL steht auf einer Custom-Domain, ist aber per
`robots.txt` + `noindex` nicht indexiert. Der saubere Weg wäre Supabase Auth (ein einzelner
Magic-Link-User) und `TO authenticated` statt `TO anon` — das ist aber ein spürbarer Umbau am
Dashboard, kein Einzeiler.

### S-2 — Drei Views umgehen RLS

Supabase-Advisor, Level **ERROR**:

- `v_etappen_uebersicht`, `v_offene_fotos`, `etappen_uebersicht` sind `SECURITY DEFINER`
- alle drei sind für `anon` per HTTP 200 lesbar
- `v_offene_fotos` liefert u.a. `quelldatei` (lokale Pfade)

Fix: `alter view … set (security_invoker = on);` — danach greift RLS des Aufrufers. Vorher prüfen,
ob die Pipeline die Views über den Service-Key liest (der bypasst RLS, also unkritisch).

### S-3 — Was ein anonymer Besucher lesen kann

Verifiziert per GET mit dem Publishable-Key:

```json
{"foto_nr":"CP24-012-022","gps_lat":42.281892,"gps_lon":-8.609044}
```

```json
{"datum":"2026-05-15","monolog_final":"Langsam komme ich in den Flow. …"}
```

Die `SELECT`-Policy auf `etappen` gilt für `PUBLIC` mit `USING(true)` — also alle 93 Spalten,
inklusive `tages_monolog`, `monolog_final`, `song_lyrics`. Plus GPS-Koordinaten deiner
Tagesetappen aus `fotos`.

Das ist keine Lücke im engeren Sinn (vieles davon veröffentlichst du ohnehin), aber GPS-Spuren
einer realen Person und ungeschnittene Monologe sind etwas anderes als ein fertiges Reel. Der
Fix wäre eine spaltenbeschränkte View für das Dashboard statt `SELECT *` auf `etappen`.

### Ergänzend aus dem Advisor

- `publish_queue`: RLS an, **keine Policy** → effektiv dicht, aber die `anon`-Grants
  (`SELECT, INSERT, UPDATE, DELETE, TRUNCATE`) sind totes Recht. Aufräumen.
- `update_modified_column`: `search_path` nicht gesetzt (WARN).
- Generell hat `anon` auf fast allen Tabellen noch `DELETE`/`INSERT`/`TRUNCATE`-Table-Grants aus
  dem Supabase-Default. Über PostgREST nicht erreichbar (RLS bzw. kein TRUNCATE-Endpunkt), aber
  ein `revoke` wäre sauberer Defense-in-Depth.

## Anhang — wie ich geprüft habe

- **Spalten-Grants:** `PATCH` mit echtem Body auf eine ID, die garantiert nichts trifft. Der
  Spalten-Grant wird beim Planen geprüft, also kommt `401` auch bei null getroffenen Zeilen —
  zerstörungsfrei und eindeutig.
- **Nicht bewiesen:** dass `DELETE` für `anon` blockiert ist. Ein `DELETE` über null Zeilen liefert
  `204`, egal ob RLS greift — derselbe Trugschluss wie oben. Der Schluss kommt aus den Policies
  (`pg_policy`: keine DELETE-Policy für `anon`), nicht aus einem Test.
- **Zeilenzahl:** `Prefer: count=exact` + `Range: 0-0` → `Content-Range: 0-0/1645`.
- **JSX-Escapes:** `@babel/standalone` lokal über die betroffene Zeile laufen lassen.
- **Advisor:** Supabase MCP `get_advisors(type: security)`.
